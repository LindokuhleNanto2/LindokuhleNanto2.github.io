Evidence 02 · User needs into work

User Stories and Tasks

The stories below express the needs of the people who use BrightStart and connect those needs to practical implementation and testing tasks. They are written in a consistent user-story format using the documented project features.

Users considered: parents/guardians, tutors and administrators

How the stories were organised

The team’s Trello board included requirements gathering, defining system features, prioritising the product backlog and dividing work into sprint-labelled groups. The user stories below translate the BrightStart functionality described in the project documentation into user-centred requirements. They should be read alongside the Trello taskboard, not as a claim that every story was copied word-for-word from a Trello card.

Prioritisation logic: account access, booking and payment are core service flows; progress tracking supports the learning purpose; staff and administrator functions support delivery and control.
US-01Parent registration and email verification

“As a parent or guardian, I want to create an account and verify my email so that I can securely access the service.”

Acceptance criteria

  • The registration form collects the required parent and learner details.
  • The account is created and email verification is required before login.
  • The user receives clear feedback when a required field is missing or registration fails.

Related tasks: Registration form; input validation; Supabase Auth registration; parent profile creation; verification and error feedback.

US-02Parent sign-in

“As a registered parent, I want to sign in so that I can access my parent portal.”

Acceptance criteria

  • Valid credentials allow access to the parent area.
  • Invalid credentials show a useful error message.
  • Pages intended for parents are not shown to signed-out users.

Related tasks: Login screen design; login form; authentication check; session handling; protected parent routes.

US-03View tutoring programmes

“As a parent, I want to view available tutoring programmes so that I can choose a suitable option for my child.”

Acceptance criteria

  • Programme information is readable and organised.
  • The parent can identify the service and the learning support offered.

Related tasks: Services page; programme content; navigation links.

US-04Book a tutoring session

“As a parent, I want to choose a programme and session time so that I can request tutoring for my child.”

Acceptance criteria

  • The parent can select the available programme and session details.
  • A valid booking is saved and its status can be displayed.
  • Missing required booking information is flagged.

Related tasks: Booking form; validation; save booking record; booking status display.

US-05Submit payment proof

“As a parent, I want to upload proof of payment so that my booking can be reviewed.”

Acceptance criteria

  • A parent can select and submit payment proof.
  • The submission creates or updates the payment record.
  • The parent can see that payment is awaiting verification.

Related tasks: Payment upload interface; storage upload; payment record; pending-verification feedback; troubleshoot payment errors.

US-06Check booking and payment status

“As a parent, I want to see booking and payment statuses so that I know whether my session is confirmed.”

Acceptance criteria

  • The portal shows the status associated with the booking/payment.
  • A pending payment is not presented as verified.
  • A verified payment can lead to a confirmed booking.

Related tasks: Status labels; retrieve booking/payment data; test status transitions.

US-07Track learner progress

“As a parent, I want to view my child’s progress so that I can understand areas of improvement.”

Acceptance criteria

  • Progress information is presented clearly.
  • Reading, writing, comprehension and speaking can be represented in progress information.
  • Only the relevant parent should access their learner’s information.

Related tasks: Progress page; progress data retrieval; parent access checks.

US-08Tutor sign-in

“As a tutor, I want to sign in with my staff account so that I can access tutor functions.”

Acceptance criteria

  • Staff credentials are authenticated.
  • The tutor role is checked before protected tutor pages are shown.

Related tasks: Staff authentication; role check; protected tutor routes.

US-09View assigned learners

“As a tutor, I want to view registered learners so that I can find the learner whose progress I need to update.”

Acceptance criteria

  • Learner records are displayed in a usable list.
  • The tutor can identify the relevant learner.

Related tasks: Tutor learner view; retrieve learner records; test role permissions.

US-10Record learner progress

“As a tutor, I want to record progress and feedback so that parents can follow a learner’s development.”

Acceptance criteria

  • Progress can be recorded against the appropriate learner.
  • Feedback is saved and displayed to authorised users.

Related tasks: Progress form; database write; progress retrieval; test data ownership.

US-11Administrator overview

“As an administrator, I want an overview of bookings, payments and learners so that I can manage service activity.”

Acceptance criteria

  • The dashboard presents relevant operational information.
  • Only authorised administrator accounts can access it.

Related tasks: Admin dashboard; data queries; role-based access.

US-12Manage bookings

“As an administrator, I want to review and manage bookings so that requests are handled correctly.”

Acceptance criteria

  • Bookings can be viewed with their current statuses.
  • Changes are saved and reflected in the system.

Related tasks: Booking management view; update logic; status testing.

US-13Verify or reject payment

“As an administrator, I want to review payment proof so that I can verify or reject a submitted payment.”

Acceptance criteria

  • The administrator can review the payment record and its proof.
  • A decision updates the payment status.
  • The related booking status reflects the payment decision.

Related tasks: Payment review view; proof access; update payment and booking records; test the payment error path.

US-14Manage learner records

“As an administrator, I want to manage learner information so that the service maintains accurate records.”

Acceptance criteria

  • Learner information is available to authorised staff.
  • Changes are saved and can be retrieved.

Related tasks: Learner management; form validation; database integration testing.

US-15Restrict access by role

“As a user, I want the website to show functions appropriate to my role so that private information is protected.”

Acceptance criteria

  • Parent, tutor and administrator functions are separated.
  • Protected pages check the user’s session and role.
  • Unauthorised access is blocked.

Related tasks: Role checks; route guards; session/logout testing; review access policies.

My reflection

User stories helped me think beyond the screen and consider the person trying to complete a task. For example, designing a login screen is not only about the layout: the user needs to understand what information to enter and what happens when something goes wrong. The payment flow made this especially clear because a parent needs useful feedback after submitting proof, while the administrator needs to review it and update the booking correctly.

As the UI/UX Designer, I contributed by designing the login and account-creation screens in Figma and by considering clear navigation and feedback. I also helped investigate the payment error and tested whether the frontend and backend worked together. This taught me that acceptance criteria are valuable because they give the team a shared way to decide whether a feature is actually working. A limitation is that stories need to be kept aligned with Trello as requirements change; a story that is written but never prioritised or tested is not enough on its own.
